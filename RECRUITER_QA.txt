================================================================================
1. THE 30-SECOND PITCH
================================================================================

Q: What is this project, in one or two sentences?
A: It's an interactive learning platform that teaches the Software Development
   Life Cycle (SDLC) two ways side by side — the traditional process and an
   AI-augmented version of the same process — through narrative pages,
   drag-and-drop quizzes, branching decision simulations, and real-world case
   studies. It's a single-page React app, fully client-side, no backend.

Q: Who is the target user?
A: Students or junior developers learning SDLC fundamentals, and anyone
   evaluating how AI tools change each phase of the lifecycle (planning,
   analysis, design, implementation, testing, deployment, maintenance, review).

Q: Why did you build this?
A: To practice building a non-trivial, fully client-side React app with real
   interactivity (drag-and-drop, branching simulations, animated transitions)
   and to have a teaching tool that contrasts classic SDLC with AI-augmented
   workflows phase by phase rather than as an abstract afterthought.

================================================================================
2. TECH STACK
================================================================================

Q: What's the stack?
A: React 19 + React Router 7, built with Vite (using the rolldown-vite engine
   for faster builds). Framer Motion for animation. @dnd-kit for accessible
   drag-and-drop. Vitest + React Testing Library for unit/integration tests,
   Cypress + cypress-axe for E2E and accessibility testing. No backend, no
   database — all content lives in JS data modules under src/constants/.

Q: Why no backend?
A: The content is static educational material; there's no user-generated data
   that needs persistence beyond the current browser session. A backend would
   add operational cost with no functional benefit. If user accounts, saved
   progress, or leaderboards were required, that's the natural next step
   (see "What would you add next").

Q: Why Vite over Create React App / Next.js?
A: Vite gives fast dev-server start and HMR; Next.js's SSR/SSG and routing
   conventions aren't needed since this is a fully client-rendered SPA with
   no SEO requirement for individual phase pages. React Router handles all
   the routing client-side.

Q: Why Framer Motion specifically?
A: It gives declarative animation (`animate`, `whileHover`, `variants`)
   without hand-rolling CSS keyframes for every interaction, and its
   AnimatePresence component is what makes exit animations on route changes
   and quiz/section transitions straightforward.

Q: Why @dnd-kit instead of react-beautiful-dnd or native HTML5 drag/drop?
A: @dnd-kit is actively maintained, has built-in keyboard sensor support
   (accessible drag-and-drop, not just mouse/touch), and supports both
   sortable-list reordering and arbitrary drop-target matching, which the
   drag-and-drop quiz needs for two different question types (ordering SDLC
   phases vs. matching terms to definitions).

================================================================================
3. ARCHITECTURE
================================================================================

Q: Walk me through the folder structure.
A:
   src/
     pages/sdlc/        - traditional SDLC phase pages (planning, analysis...)
     pages/ai-sdlc/      - AI-augmented counterparts of the same 8 phases
     components/         - shared interactive components (Quiz, DragDropQuiz,
                            SimulationEngine, SimulationHub, CaseStudy, Menu,
                            OutcomeTracker, NetworkBackground, etc.)
     constants/sdlc/      - content data for traditional pages (steps, quizzes,
                            drawbacks/pitfalls, simulation scenarios)
     constants/ai-sdlc/   - equivalent content for the AI-augmented pages
     constants/quiz/      - quiz question banks per phase
     constants/simulation/- branching decision-tree data for the simulation
                            engine
     styles/index.js      - centralized inline-style design system shared by
                            every page/component
     test/                - Vitest setup, mocks, and shared test utilities

Q: Why is styling done with a centralized JS object (styles/index.js) instead
   of CSS Modules, Tailwind, or styled-components?
A: It's a single source of truth for the whole design system — every spacing,
   color, and animation value lives in one importable object, so any page can
   do `import styles from '../../styles'` and reuse `styles.pageContainer`,
   `styles.nextButton`, etc. without re-declaring CSS classes per page. The
   trade-off is the file is large (~5,800 lines) and some color/spacing
   values were duplicated rather than composed — that's a known maintenance
   cost I'd address with a proper token system or CSS variables if I extended
   this further (see "What would you refactor").

Q: Why are the SDLC and AI-SDLC phase pages separate files instead of one
   parameterized component?
A: They started as near-duplicates and have stayed structurally identical
   (same section flow: intro → visualization → steps → types → drawbacks →
   joke break → quiz) but render different content. That repetition is the
   single biggest refactor opportunity in the codebase — a `<PhasePage
   variant="ai" data={...} />` pattern would cut ~5,000 lines of duplicated
   JSX. I haven't done it because the two tracks (traditional vs AI) evolved
   independent narrative beats and didn't stay perfectly parallel, but it's
   the first thing I'd tackle with more time.

Q: How does routing work?
A: React Router's `<Routes>`/`<Route>` in App.jsx, one route per phase per
   track (e.g. `/planning` and `/ai-planning`), plus dynamic routes for
   simulations (`/simulation/:type/:scenarioId`), case studies
   (`/case-study/:type/:caseId`), and the drag-and-drop quiz
   (`/drag-drop-quiz/:type`). All routes are wrapped in a `PageTransition`
   component and rendered inside `AnimatePresence` keyed on the current
   pathname, so navigating between pages animates instead of hard-cutting.

================================================================================
4. KEY FEATURES — BE READY TO DEMO/EXPLAIN EACH
================================================================================

Q: What are the interactive pieces, concretely?
A:
   1. Phase pages (16 total: 8 traditional + 8 AI) — each is a multi-section
      narrative with a process visualization, a "drawbacks & resolutions"
      reveal interaction, and an embedded quiz.
   2. Quiz component — multiple choice, answer locking, inline explanation
      feedback per question.
   3. DragDropQuiz — two question types built on @dnd-kit: reordering SDLC
      phases into the correct sequence, and matching terms to definitions via
      drop targets. Has a countdown timer per question and a scored results
      screen.
   4. SimulationEngine / SimulationHub — branching decision simulations.
      You're given a project scenario, make a decision at each phase, and an
      OutcomeTracker shows how that decision moved metrics (budget, timeline,
      quality, team morale, and — for AI scenarios — an "AI efficiency"
      metric) in real time, ending in a results screen with lessons learned.
   5. CaseStudy / CaseStudyList — real-world style scenarios with a pass/fail
      scored outcome.
   6. Menu — a reusable animated dropdown nav used on every page, highlights
      the current route.

Q: How does the simulation engine track state across multiple decisions?
A: `OutcomeTracker` is fed `context` (current metric values) and
   `initialContext` (starting values) as props on every render. Each
   metric's color (green/amber/red) is computed by comparing current vs
   initial — for cost/timeline lower is better, for quality/satisfaction
   higher is better — so the same component visualizes inverse-direction
   metrics correctly with one formatting function (`getProgressColor`).

Q: How is quiz/simulation data modeled?
A: Plain JS arrays/objects per phase under `src/constants/`, e.g. a
   `planningQuiz` array of `{question, options[], correctIndex, explanation}`
   objects, and simulation scenarios as `{id, title, initialContext, decisions[]}`
   trees. No schema validation library — it's trusted local data, not user
   input, so that's an intentional simplicity trade-off.

5. UI / DESIGN DECISIONS (recent work in this session)
================================================================================

Q: The UI uses no emoji or images anywhere — was that a deliberate choice?
A: Yes. The app originally used emoji glyphs as ad-hoc icons (over 1,400
   occurrences across 60+ files) plus a couple of raster images on the
   homepage. I stripped all of it and replaced icon-shaped UI with small
   animated CSS/SVG accents (gradient bars, pulsing dots) driven by color and
   motion instead of pictographic icons — gives a more deliberate, designed
   look and renders identically across OS/browser emoji font differences.

Q: What's the animated background on the homepage?
A: A custom `NetworkBackground` component — a generative SVG of nodes and
   connecting lines that pulse and "flow" via CSS keyframe animation,
   suggesting a development pipeline. It's pure SVG + CSS, intentionally not
   framer-motion's SVG primitives (`motion.line`/`motion.circle`), because
   those didn't reconcile reliably under the test renderer — using plain SVG
   elements with CSS `@keyframes` instead sidesteps that and is simpler.

Q: How do page transitions work?
A: `PageTransition` is a small wrapper (`motion.div` with
   `initial`/`animate`/`exit`) applied to every route's element in App.jsx,
   combined with `<AnimatePresence mode="wait">` around a `<Routes>` keyed on
   `location.pathname`. That's the standard React Router + Framer Motion
   pattern for route-level enter/exit animation.

Q: Tell me about the color system.
A: It's a single teal/blue brand family (`#38b2ac` → `#319795` → `#4bb1b4` →
   `#325fa1` and a few neighboring shades) used consistently for primary
   actions, accents, and the 8-stage progression on the learning hub. I did a
   pass removing several inconsistent saturated colors that had crept in
   (purple, orange, gold, neon cyan/yellow) and replaced them with shades
   from that same family so distinct UI elements (buttons, badges, stage
   markers) read as part of one system rather than a rainbow of one-off
   choices. Semantic colors (success green / warning amber / error red used
   for quiz feedback and simulation health indicators) were deliberately left
   alone — those communicate meaning, not brand, and shouldn't be "fixed" to
   match the palette.

Q: Is the layout responsive?
A: Yes — fluid typography via CSS `clamp()` throughout, CSS Grid with
   `auto-fit`/`minmax()` for card layouts, and a dedicated breakpoint for the
   floating section-navigation pill: it's a vertical strip on the left edge
   at desktop widths and collapses into a horizontal scrollable bar pinned to
   the bottom of the screen under 768px, so it never overlaps body copy on a
   phone-width viewport.

Q: What other small UX additions did you make?
A: A slim scroll-progress bar fixed to the top of the viewport (fills as you
   scroll a long phase page), and a scroll-to-top floating button that
   appears once you've scrolled past ~60% of a viewport height.

Q: Did you consider a light/dark theme toggle?
A: I looked at it and deliberately did not ship it half-working. The app's
   colors are hardcoded inline per-component in styles/index.js rather than
   driven by CSS custom properties, so a real toggle would mean threading a
   theme value through thousands of inline style declarations — not a
   `:root` variable flip. Shipping a toggle that only changed the page
   background while every card/button stayed dark would be worse than not
   having the feature. It's flagged as a real follow-up, not skipped
   carelessly.

================================================================================
6. TESTING
================================================================================

Q: What's covered by tests?
A: 148 tests across 14 files: every SDLC and AI-SDLC page, the shared
   components (Quiz, Menu, CaseStudy, DragDropQuiz), and an integration suite
   that renders all pages, checks navigation/back-links/menu presence on
   every one, accessibility heading structure, error-handling with
   missing/malformed data, and memory-leak/unmount behavior.

Q: What's your testing stack and why?
A: Vitest (Vite-native, fast, Jest-compatible API) + React Testing Library
   (tests behavior/DOM output, not implementation detail) for unit/integration,
   and Cypress + cypress-axe for end-to-end flows and automated accessibility
   checks in a real browser.

Q: How do you handle mocking framer-motion and react-router in tests?
A: Global mocks in `src/test/setup.js` replace `motion.div/h1/h2/h3/p/button/
   section/span` with plain DOM elements and `AnimatePresence` with a
   passthrough, and stub `useNavigate`/`useParams`/`useLocation` and
   `MemoryRouter`/`Link`. This keeps tests fast and deterministic — no
   animation timing flakiness — at the cost of needing to remember the mock
   only covers tags it explicitly lists (I hit this directly: adding
   `motion.span` to the Menu component broke a test file that had its own
   local, narrower framer-motion mock not including `span`; fixed by using a
   plain CSS-transitioned `<span>` instead of relying on the animation
   library for a one-property rotation).

Q: Did you find and fix any actual bugs while doing this pass?
A: Yes, several pre-existing ones, found because tooling caught them once I
   started touching adjacent code:
   - A malformed/unterminated JSDoc comment block in styles/index.js was
     silently breaking the Vitest runner (oxc parser choked on stray text
     outside a comment).
   - Two unclosed JSX comments in App.jsx (`{/* ... */` missing the closing
     `}`) were breaking the *production build* outright — `npm run build`
     failed with a parser error before this was fixed.
   - The "Learn Software Development" hub's stage circles had no visible
     background color at all: the component read `stage.color` but the data
     file never defined a `color` field, so it silently rendered `undefined`.
   - A handful of `score >= threshold ? '<emoji>' : '<emoji>'` ternaries
     became `'' : ''` after I stripped emoji content, leaving dead
     conditional logic with no visible effect — cleaned up to a plain
     decorative element.

Q: Why does the test suite occasionally show a flaky timeout?
A: Under full-parallel `vitest run` on a resource-constrained machine, a
   couple of integration tests that render 8+ full pages back-to-back can
   exceed the default 5s test timeout purely from CPU contention with the
   other 13 test files running concurrently — they pass consistently and
   quickly (under 2s) in isolation. I bumped `testTimeout` to 15s in
   `vite.config.js` as a pragmatic fix rather than chasing a phantom logic
   bug that isn't there.

================================================================================
7. PERFORMANCE
================================================================================

Q: What's the production bundle size, and are you worried about it?
A: ~1.15 MB JS (~275 KB gzipped) in a single chunk — Vite's build warns past
   500 KB. It's worth flagging proactively: with 16 near-identical phase
   pages, every route's code currently ships in one bundle. The fix is
   route-based code-splitting with `React.lazy()` per page plus
   `manualChunks` in the Rollup/Rolldown config, which I'd prioritize before
   scaling content further — I didn't do it in this pass because it's a
   structural change worth its own focused PR and testing pass, not a
   drive-by edit.

Q: Any other performance considerations?
A: Animations are CSS/SVG-driven where possible (the network background, the
   decorative accent pulses) specifically to avoid layout thrashing from
   JS-driven animation loops on a page with many simultaneous animated
   elements.

================================================================================
8. ACCESSIBILITY
================================================================================

Q: What accessibility work has been done?
A: cypress-axe is wired in for automated a11y checks in E2E tests.
   @dnd-kit's KeyboardSensor means the drag-and-drop quiz is operable via
   keyboard, not just pointer. Heading structure (h1/h2/h3) is checked in the
   integration test suite. Focus-visible outlines are defined globally for
   buttons.

Q: What would you still improve for accessibility?
A: Color contrast hasn't been formally audited against WCAG AA across every
   text/background combination in styles/index.js — that's a sizeable file
   and a dedicated contrast pass (ideally automated, e.g. via axe in CI)
   would be the next step. The floating circular nav buttons rely on visual
   position; I'd want to double-check screen-reader announcement order
   matches visual order after the responsive bottom-bar collapse.

9. "HOW WAS THIS BUILT" / AI-ASSISTED DEVELOPMENT
================================================================================

Q: Did you use AI tools to build this?
A: Yes, extensively and deliberately — the repo includes
   AI-SDLC-PROJECT-CREATION.txt documenting how AI-augmented practices were
   applied across every phase of building this exact project (AI-assisted
   architecture decisions, component scaffolding, and a later pass using an
   AI coding agent to do a large mechanical refactor: stripping ~1,400 emoji
   characters across 60+ files, fixing structural fallout from that, adding
   new interactive features, and auditing the color system). I can speak to
   exactly what I asked it to do, what I checked by hand afterward (running
   the full test suite and production build after every batch of changes,
   not just trusting the diff), and where I overrode or scoped down a
   suggestion (e.g. declining to ship a half-working theme toggle).

Q: How do you verify AI-assisted changes are actually correct?
A: The same way as any change: run the full test suite (148 tests) and a
   production build after each meaningful batch of edits, not just visually
   skim the diff. Several of the bugs listed in section 6 were only caught
   because the build/test loop was run repeatedly and treated as a gate, not
   a formality.

Q: What's a concrete example of where an automated/mechanical approach broke
   something, and how did you catch it?
A: Stripping emoji characters via a regex script left several UI elements
   with empty content where an emoji used to be the only child (icon-only
   nav buttons, decorative "hero icon" containers). A blind regex pass alone
   would have shipped empty, confusing buttons. I followed it with a second
   pass specifically hunting for now-empty interactive elements and either
   gave them real text labels (nav buttons) or restyled the container itself
   as a deliberate decorative element (CSS gradient bars/dots) so nothing
   regressed silently.

10. WHAT WOULD YOU DO DIFFERENTLY / NEXT STEPS
================================================================================

Q: If you had another two weeks, what's the priority order?
A:
   1. Collapse the 16 near-duplicate phase pages into one data-driven
      `PhasePage` component — biggest maintainability win, biggest line-count
      reduction.
   2. Route-based code-splitting to address the single 1.1 MB bundle.
   3. Migrate styles/index.js's hardcoded colors to CSS custom properties so
      a real theme toggle (and easier global re-theming) becomes possible.
   4. A WCAG contrast audit pass.
   5. Persist simulation/quiz progress (localStorage at minimum, a real
      backend if accounts are ever wanted) — right now all progress is
      lost on refresh.

Q: What's the single biggest piece of technical debt in this codebase?
A: The duplicated phase-page structure (point 1 above). It's also exactly
   why the recent UI pass — removing emoji, fixing the floating nav,
   restyling icon containers — had to be done with small scripts applied
   across 16 files rather than a single component edit; a refactor to one
   parameterized component would have made every one of those changes a
   one-file diff instead.

Q: Why didn't you do the big refactor (item 1) while you were already
   touching every one of those files for the emoji/color pass?
A: Scope discipline — the ask was a UI/content pass, not a structural
   rewrite, and merging "remove emoji" with "restructure the component tree"
   in the same change would make the diff much harder to review and much
   riskier to revert if something broke. Structural refactors deserve their
   own isolated change with its own test pass.
